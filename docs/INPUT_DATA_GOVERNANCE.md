# تفکیک تنظیمات، داده‌های ورودی و داده‌های تحلیلی — MANG_01
**شناسه:** MANG-DATA-GOV-001 | **نسخه:** 1.0.0 | **وضعیت:** الزام معماری؛ مقادیر کسب‌وکاری و انتساب مسئولیت‌های واقعی نیازمند تصویب‌اند.

## 1. الزام بنیادین
سامانه باید سه نوع داده را از نظر معنا، مالکیت، چرخه عمر، UI، ذخیره‌سازی، مجوز و ممیزی کاملاً از هم تفکیک کند. این سه نوع نباید در یک فرم، جدول یا مسیر پردازشی مبهم ادغام شوند:

1. **تنظیمات سیستم (System Settings / Policy Parameters):** پارامترهایی که رفتار، تفسیر یا آستانه‌های سامانه را تعیین می‌کنند؛ مانند «تاب‌آوری نقدینگی». تنظیمات کسب‌وکاری باید دارای تعریف، واحد/مقیاس، دامنه اعتبار، مالک، وضعیت تصویب، تاریخ اثر و نسخه باشند. تغییر آنها داده تاریخی را بازنویسی نمی‌کند.
2. **داده‌های ورودی (Input / Source Data):** واقعیت‌ها یا مقادیر پایه‌ای که افراد مجاز به‌صورت دستی یا از طریق فایل وارد می‌کنند. برای هر قلم باید دقیقاً مشخص باشد چه نقش/فردی، کدام فیلدها را، برای چه دوره‌ای، با چه فرکانسی، تا چه موعدی، با چه روشی و تحت چه تأییدی وارد می‌کند. انتساب نهایی افراد، فیلدها و تناوب‌های واقعی تا تصویب ماتریس مجاز نیست.
3. **داده‌های تحلیلی (Derived / Analytical Data):** خروجی محاسبات قطعی و قابل توضیح روی تنظیمات مصوب و داده‌های ورودی معتبر و نسخه‌بندی‌شده؛ از جمله KPI، انحراف، روند، پیش‌بینی، ریسک و پیشنهاد تصمیم. این داده‌ها مستقیماً توسط کاربر ویرایش نمی‌شوند؛ با تغییر ورودی/تنظیمات، محاسبه مجدد و نسخه جدید تولید می‌شود.

### 1.1 قواعد غیرقابل نقض
- هر قلم داده دقیقاً یک طبقه اصلی دارد: SETTING، INPUT یا ANALYTICAL. طبقه‌های فرعی ممکن‌اند اما این طبقه اصلی اجباری است.
- داده تحلیلی نباید به‌عنوان داده ورودی یا واقعیت تأییدشده نمایش داده شود.
- تنظیمات و ورودی‌ها دارای تاریخچه نسخه و Audit Trail هستند؛ مقدار قبلی حذف یا بی‌ردپا بازنویسی نمی‌شود.
- تحلیل باید به نسخه دقیق داده‌های ورودی، نسخه تنظیمات، نسخه فرمول/موتور، زمان اجرا و وضعیت اعتبارسنجی ارجاع دهد.
- ورودی ناقص، منقضی، نامعتبر یا تأییدنشده باید در محاسبه مطابق سیاست مصوب رد یا با محدودیت آشکار لحاظ شود؛ هیچ مقدار پیش‌فرض پنهانی مجاز نیست.
- فرمول، آستانه، واحد، نقش، تناوب و قاعده تأییدِ تعریف‌نشده باید «نیازمند تأیید» باشد؛ عامل توسعه نباید آن را حدس بزند.
- همه تاریخ‌ها، timezone، واحدها، ارز/مقیاس و دوره گزارش باید صریح باشند. تبدیل ضمنی یا تغییر واحد بی‌ردپا ممنوع است.
- داده‌های DEMO و REAL از نظر محیط/منبع و نمایش جدا هستند.

## 2. تفکیک در UI و ناوبری
منوی اصلی باید سه فضای مستقل و قابل تشخیص داشته باشد:

### A. «تنظیمات سیستم»
- فهرست تنظیمات با کد، عنوان، توضیح، نوع، واحد/مقیاس، مقدار جاری، نسخه، تاریخ اثر، مالک، وضعیت تصویب و آخرین تغییر.
- فرم جزئیات/ویرایش با نمایش مقدار فعلی و پیشنهادی، دلیل تغییر، تاریخ اثر و اثرات وابسته.
- برای پارامتر مؤثر بر تحلیل، تغییر تا تصویب نقش مجاز در وضعیت PENDING_APPROVAL بماند؛ اگر گردش تصویب هنوز تعیین نشده، قابلیت انتشار غیرفعال باشد.
- امکان مشاهده تاریخچه و مقایسه نسخه‌ها.
- تغییر تنظیمات باید تحلیل‌های متأثر را stale علامت بزند و نیاز به محاسبه مجدد را ثبت کند.
- نمونه مفهومی: «تاب‌آوری نقدینگی». تعریف عملیاتی، روش اندازه‌گیری، واحد/مقیاس، محدوده مجاز و مالک آن هنوز باید تصویب شود؛ عدد یا فرمول نمونه در محیط REAL درج نشود.

### B. «ورود داده‌های پایه و مستر دیتا»
این بخش یک قابلیت اصلی سامانه است، نه صفحه فرعی یا صرفاً ابزار فنی مدیر سیستم.
- صفحه خانه ورود داده با دسته‌بندی حوزه‌ها، وظایف باز، موعدها، داده‌های ناقص/کهنه، وضعیت تأیید و آخرین ثبت کاربر.
- فرم ورود گروهی/تک‌قلمی متناسب با نوع داده؛ ذخیره پیش‌نویس، اعتبارسنجی، ارسال برای تأیید در صورت نیاز، اصلاح خطا و مشاهده تاریخچه.
- صفحه «ماتریس ورود داده» برای تعیین قلم/فیلد، مالک داده، ثبت‌کننده، تأییدکننده، تناوب، موعد، روش ورود، منبع، قواعد اعتبارسنجی و پیامد تأخیر.
- قالب Excel نسخه‌دار باید از همین ماتریس تولید یا به آن متصل شود؛ فیلدهای ناشناخته یا ستون‌های اجباری حذف‌شده نباید بی‌صدا پذیرفته شوند.
- ورود دستی و Excel باید از همان قواعد دامنه، کنترل دسترسی، اعتبارسنجی و ممیزی استفاده کنند.
- برای کاهش بار کاری: ورود مجدد داده بدون تغییر اجتناب شود؛ فرم‌ها فقط فیلدهای مجاز همان نقش/دوره را نمایش دهند؛ مقادیر قبلی صرفاً به‌صورت مقدار پیشنهادی با منبع و تاریخ دیده شوند و بدون تأیید خودکار به‌عنوان واقعیت جدید ثبت نشوند؛ ورود گروهی، کپی دوره قبل، autosave پیش‌نویس و اعتبارسنجی قبل از ارسال پشتیبانی شود، مشروط به ثبت منشأ و تأیید کاربر.
- سامانه باید برای هر دوره مشخص کند چه اقلامی لازم‌اند، کدام تکمیل شده، کدام در انتظار تأیید و کدام معوق‌اند؛ موعد و تناوب فقط از ماتریس مصوب خوانده شود.

### C. «تحلیل‌ها و خروجی‌ها»
- فقط خروجی‌های محاسبه‌شده توسط موتور تحلیل نمایش داده شوند.
- هر خروجی باید تعریف، مقدار/واحد، دوره، وضعیت، زمان محاسبه، نسخه فرمول، ورودی‌های استفاده‌شده، نسخه تنظیمات و توضیح قابل فهم از روش محاسبه را نشان دهد.
- اگر داده کافی یا معتبر نیست، نتیجه NOT_COMPUTABLE، PARTIAL یا وضعیت معادل مصوب نمایش داده شود؛ مقدار صفر/سبز/عادی جایگزین نشود.
- ویرایش مستقیم نتیجه تحلیلی ممنوع؛ اصلاح باید در تنظیمات یا داده ورودی انجام و تحلیل دوباره اجرا شود.
- امکان Drill-down از نتیجه تحلیلی به داده‌های مبنا و از داده مبنا به سابقه تغییرات وجود داشته باشد.

## 3. ماتریس ورود داده دستی — ساختار الزامی
ماتریس زیر **الگوی حاکمیتی** است. نقش‌ها، اقلام دقیق، تناوب‌ها و موعدها نمونه قطعی نیستند و باید با مالکان واقعی داده تکمیل و تصویب شوند. تا آن زمان، هر ردیف در وضعیت DRAFT / NEEDS_APPROVAL می‌ماند و برنامه نباید وظیفه عملیاتی یا موعد ساختگی ایجاد کند.

| فیلد ماتریس | توضیح/قاعده |
|---|---|
| data_item_code | کد یکتای قلم ورودی |
| data_item_name | نام فارسی و نام انگلیسی در صورت نیاز |
| business_definition | تعریف روشن و معیار شمول/عدم شمول |
| domain | حوزه کسب‌وکار مصوب |
| field_schema | نام فیلد، نوع داده، اجباری/اختیاری، طول/دقت |
| unit_currency_scale | واحد، ارز و مقیاس؛ در صورت کاربرد |
| period_basis | نقطه‌ای، روزانه، هفتگی، ماهانه یا تعریف مصوب دیگر |
| data_owner_role | پاسخ‌گوی تعریف و کیفیت داده |
| entry_role_or_person | نقش/فرد مسئول ورود؛ انتساب فردی با تصویب |
| approver_role | تأییدکننده در صورت نیاز؛ تا تعیین، گردش تأیید فرض نشود |
| frequency | تناوب مصوب، نه مقدار پیش‌فرض |
| deadline_rule | موعد دقیق یا قاعده موعد؛ نیازمند تأیید |
| entry_method | فرم، ورود گروهی، Excel یا منبع مصوب |
| authoritative_source | منبع اصلی و مرجع حل تعارض |
| validation_rules | دامنه، فرمت، ارتباطات و قواعد سازگاری |
| late_data_policy | رفتار داده معوق؛ نیازمند تصویب |
| correction_policy | اصلاح، جایگزینی، ابطال و ثبت دلیل |
| approval_status | Draft / Pending Approval / Approved / Retired |
| effective_from/to | بازه اعتبار نسخه ماتریس |
| estimated_entry_effort | زمان تقریبی ثبت، پس از اندازه‌گیری واقعی |
| last_reviewed_at/by | بازبینی و مالک بازبینی |

### 3.1 ماتریس اولیه برای تکمیل با مالکان داده
| قلم/گروه داده | طبقه | ثبت‌کننده پیشنهادی برای تعیین تکلیف | فرکانس | روش ورود | وضعیت |
|---|---|---|---|---|---|
| پارامتر تاب‌آوری نقدینگی | SETTING، نه ورودی دوره‌ای | مالک کسب‌وکار/مالی که باید تعیین و تصویب شود | هنگام تصویب/بازنگری؛ قاعده دقیق نیازمند تأیید | فرم تنظیمات با نسخه و دلیل | نیازمند تأیید |
| داده‌های پایه مالی و نقدینگی موردنیاز تحلیل | INPUT | مالک داده مالی که باید تعیین شود | نیازمند تأیید بر اساس تصمیم مورد استفاده | فرم/Excel مصوب | نیازمند تعریف فیلد و تأیید |
| اطلاعات پایه حوزه‌ها و مراکز مسئولیت | INPUT / MASTER DATA | مالک هر دامنه که باید تعیین شود | رویدادمحور یا دوره‌ای؛ نیازمند تأیید | UI مستر دیتا/ورود گروهی | نیازمند تأیید |
| داده‌های وضعیت تعهدات/پروژه‌ها، در صورت تأیید دامنه | INPUT | مالک حوزه مربوط که باید تعیین شود | نیازمند تأیید | فرم/Excel؛ اتصال سیستمی فقط پس از تصویب | نیازمند تأیید |
| شاخص‌های عملکرد و وضعیت ریسک محاسبه‌شده | ANALYTICAL | سامانه؛ مالک کسب‌وکار نتیجه را بازبینی می‌کند | پس از ورود/تغییر داده و اجرای محاسبه طبق سیاست | موتور محاسبات | ورودی دستی نیست |

این جدول فهرست قطعی همه داده‌های کسب‌وکار نیست؛ صرفاً قالب آغاز کار است. فهرست واقعی داده‌ها باید از تعریف مصوب شاخص‌ها، منابع رسمی و تصمیم‌های مورد نیاز استخراج و تأیید شود.

## 4. مدل داده و موجودیت‌های پیشنهادی
موجودیت‌های زیر باید در مدل مفهومی/API در نظر گرفته شوند. نام نهایی جدول‌ها قابل تغییر است، اما معنای تفکیک‌شده باید حفظ شود.

| موجودیت | مسئولیت و فیلدهای کلیدی |
|---|---|
| setting_definition | code, name, description, value_type, unit, validation_schema, owner, approval_required, status |
| setting_version | setting_id, version, value, effective_from/to, status, change_reason, created_by/at, approved_by/at |
| input_data_definition | code, name, business_definition, schema, unit, domain, owner, source_policy, status |
| input_responsibility_matrix | data_definition_id, entry_role, owner_role, approver_role, frequency_rule, deadline_rule, method, validation_policy, effective dates, approval status |
| input_record | definition_id, period/effective_at, typed_value/payload, source, status, submitted_by/at, approved_by/at, version, correction_reason |
| analytical_definition | code, name, formula/specification, output_schema, unit, engine_version, required_inputs, status |
| analytical_run | run_id, started_at, finished_at, status, engine_version, settings_snapshot_id, input_snapshot_id, initiated_by/trigger, diagnostics |
| analytical_result | run_id, definition_id, dimensions/period, result_value/payload, unit, confidence/status where defined, explanation/lineage |
| data_snapshot | immutable snapshot identity, dataset/version references, created_at, checksum where appropriate |
| audit_event | actor, timestamp, action, entity type/id, before/after reference or safe diff, reason, request_id |
| data_entry_task | matrix row/version, target period, assigned role/user, due date, task state, reminders/history |

قواعد فنی:
- مقدارهای دارای نوع مختلف با نوع داده کنترل‌شده ذخیره شوند؛ استفاده از یک رشته عمومی برای تمام مقادیر بدون schema ممنوع است.
- نسخه ماتریس مسئولیت باید همراه هر وظیفه و رکورد قابل بازیابی باشد تا تغییر بعدی ماتریس سابقه را عوض نکند.
- برای داده مالی/حساس، جزئیات قبل/بعد در audit طبق سیاست امنیتی ماسک یا محدود شود؛ اصل ثبت تغییر باید باقی بماند.
- محاسبه تحلیلی با snapshot immutable یا ارجاع نسخه‌ای معادل انجام شود؛ محاسبه قبلی با تغییر داده پاک یا overwrite نشود.
- source, observed_at, effective_at, entered_by, validation_status و approval_status در صورت انطباق با معنای قلم داده اجباری‌اند.
- برای اصلاح رکورد تأییدشده، نسخه اصلاحی/رویداد اصلاح ایجاد شود؛ تغییر بی‌ردپا ممنوع.
- نگاشت API، DTO، UI و پایگاه داده باید از یک Data Dictionary نسخه‌دار پیروی کند.

## 5. چرخه عمر داده
1. **تعریف:** ثبت تعریف و schema در وضعیت Draft.
2. **تعیین مالکیت:** تکمیل ماتریس مسئولیت، تناوب، موعد، منبع و قواعد اعتبارسنجی.
3. **تصویب:** تأیید مالک مجاز؛ تا آن زمان وظیفه و محاسبه وابسته فعال نشود.
4. **جمع‌آوری:** ایجاد وظیفه برای دوره مصوب و نمایش فقط فیلدهای مربوط به کاربر مجاز.
5. **اعتبارسنجی:** بررسی نوع، واحد، دامنه، دوره، منبع، تکرار و سازگاری بین فیلدها.
6. **ارسال/تأیید:** مطابق گردش مصوب؛ نبود گردش مصوب نباید با تأیید خودکار جبران شود.
7. **انتشار ورودی معتبر:** مقدار نسخه‌دار و قابل ردیابی می‌شود.
8. **محاسبه:** موتور قطعی از snapshot ورودی و نسخه تنظیمات/فرمول استفاده می‌کند.
9. **بازبینی:** کاربر نتیجه و مسیر منشأ را مشاهده می‌کند؛ نتیجه مستقیماً قابل ویرایش نیست.
10. **اصلاح و یادگیری:** اصلاح از مسیر داده اصلی؛ اجرای مجدد تحلیل و ثبت علت/نتیجه.

## 6. حداقل فشار کاری و UX ورود
- هر کاربر پس از ورود باید فهرست «وظایف داده‌ای من» را بر اساس نقش و ماتریس مصوب ببیند.
- فرم بر اساس قلم داده و schema پیکربندی شود؛ فرم عمومی بی‌ساختار جایگزین تعریف داده نشود.
- فیلدهای مشترک یک بار در هر گردش وارد شوند؛ ورودی‌های گروهی و import برای تکرارهای ساختاریافته فراهم باشد.
- امکان ذخیره پیش‌نویس و بازگشت به آن بدون ثبت به‌عنوان داده تأییدشده وجود داشته باشد.
- اعتبارسنجی اولیه در UI برای بازخورد سریع و اعتبارسنجی نهایی در backend الزامی است.
- خطاها کنار فیلد/ردیف مشخص شوند؛ کاربر مجبور به ارسال مجدد کل مجموعه برای خطای یک قلم نباشد.
- پیشنهاد مقدار قبلی باید تاریخ، منبع و وضعیت آن را نشان دهد؛ کپی‌کردن باید اقدام صریح کاربر باشد و یک رکورد جدید با تاریخ/دوره جدید بسازد.
- تکراری بودن با کلیدهای تجاری/دوره‌ای مصوب تشخیص داده شود؛ رکورد تکراری بی‌صدا overwrite نشود.
- گزارش کارکرد ورود، زمان تکمیل، تعداد اصلاح‌ها و خطاهای پرتکرار برای بهبود فرایند قابل استخراج باشد؛ این معیارها برای ارزیابی افراد بدون سیاست مصوب استفاده نشوند.
- reminder و escalation تنها پس از تصویب موعد، گیرنده و سیاست اطلاع‌رسانی فعال شوند.

## 7. APIهای موردنیاز
مسیرهای زیر به‌عنوان قرارداد طراحی لازم‌اند؛ پیاده‌سازی باید با API_CONTRACTS.md هم‌راستا و نسخه‌بندی شود.

| Method / Path | کاربرد |
|---|---|
| GET /api/v1/settings/definitions | فهرست تنظیمات و وضعیت |
| GET /api/v1/settings/{code}/versions | تاریخچه نسخه‌ها |
| POST /api/v1/settings/{code}/versions | پیشنهاد نسخه جدید، نه انتشار خودکار |
| POST /api/v1/settings/{code}/versions/{version}/approve | تصویب توسط نقش مجاز، اگر workflow مصوب باشد |
| GET /api/v1/input-definitions | فهرست اقلام ورودی |
| GET /api/v1/input-responsibility-matrix | ماتریس مسئولیت مصوب/پیش‌نویس بر اساس مجوز |
| POST /api/v1/input-responsibility-matrix | ایجاد/ویرایش نسخه پیشنهادی ماتریس |
| GET /api/v1/data-entry-tasks/mine | وظایف کاربر فعلی |
| POST /api/v1/input-records | ثبت پیش‌نویس/ورودی طبق مجوز |
| POST /api/v1/input-records/{id}/submit | ارسال برای اعتبارسنجی/تأیید |
| GET /api/v1/input-records/{id}/history | تاریخچه رکورد |
| GET /api/v1/analytical-definitions | تعریف تحلیل‌های مصوب |
| POST /api/v1/analytical-runs | اجرای محاسبه مجاز |
| GET /api/v1/analytical-runs/{id}/lineage | ورودی‌ها، تنظیمات و نسخه موتور استفاده‌شده |
| GET /api/v1/analytical-results/{id} | نتیجه تحلیلی و توضیح |

اگر گردش تأیید یا نقش مجاز هنوز مصوب نیست، endpoint تأیید باید غیرفعال بماند یا فقط عملیات پیشنهادی را بپذیرد؛ endpoint نباید به‌طور ضمنی تأیید خودکار کند.

## 8. مجوزها و ممیزی
مجوزها باید در سطح عمل و دامنه داده کنترل شوند، نه صرفاً در سطح منو:
- مشاهده تنظیمات؛ پیشنهاد تغییر تنظیمات؛ تصویب/انتشار تنظیمات.
- مشاهده تعریف داده؛ پیشنهاد تغییر ماتریس؛ تصویب ماتریس.
- ایجاد/اصلاح ورودی پیش‌نویس؛ ارسال؛ تأیید؛ ابطال/اصلاح رکورد منتشرشده.
- اجرای تحلیل؛ مشاهده نتیجه؛ مشاهده lineage.
- مشاهده audit فقط برای نقش مجاز.

نقش‌های فوق **توانمندی‌های دسترسی** هستند، نه نام نقش‌های سازمانی قطعی. نگاشت آنها به افراد/سمت‌های واقعی باید تصویب شود. ثبت audit حداقل شامل actor، زمان، عمل، موجودیت، شناسه، دلیل تغییر در صورت الزام، نتیجه، request ID و ارجاع امن به نسخه قبل/بعد است. کاربران عادی نباید بتوانند audit را تغییر یا حذف کنند.

## 9. معیارهای پذیرش الزامی
- [ ] UI سه بخش مستقل «تنظیمات سیستم»، «ورود داده‌های پایه و مستر دیتا» و «تحلیل‌ها و خروجی‌ها» دارد.
- [ ] نوع SETTING، INPUT یا ANALYTICAL برای هر تعریف داده مشخص است.
- [ ] تغییر تنظیمات نسخه جدید ایجاد می‌کند و تاریخچه قبلی باقی می‌ماند.
- [ ] ماتریس مسئولیت، ثبت‌کننده، مالک، تأییدکننده، فیلدها، فرکانس، موعد، روش، منبع و قواعد اعتبارسنجی را پشتیبانی می‌کند.
- [ ] موارد تأییدنشده در ماتریس به وظیفه عملیاتی یا موعد ساختگی تبدیل نمی‌شوند.
- [ ] ورود دستی و Excel از تعریف و قواعد اعتبارسنجی یکسان استفاده می‌کنند.
- [ ] هر ورودی ثبت‌شده به کاربر، زمان، منبع، دوره و نسخه تعریف/ماتریس مرتبط است.
- [ ] اصلاح ورودی/تنظیمات تاریخچه را حفظ می‌کند و تحلیل وابسته را stale علامت می‌زند.
- [ ] نتیجه تحلیلی به نسخه دقیق ورودی‌ها، تنظیمات و موتور محاسبه قابل ردیابی است.
- [ ] نتیجه تحلیلی مستقیماً قابل ویرایش نیست.
- [ ] داده نامعتبر/ناقص موجب نتیجه گمراه‌کننده یا مقدار پیش‌فرض پنهان نمی‌شود.
- [ ] پیشنهاد مقدار قبلی هرگز بدون اقدام صریح کاربر به‌عنوان داده جدید ثبت نمی‌شود.
- [ ] مجوزهای ثبت، تصویب، تحلیل و مشاهده تاریخچه در backend آزموده می‌شوند.
- [ ] آزمون‌های واحد/یکپارچه برای تغییر نسخه، تأیید، رد، اصلاح، import تکراری، lineage و جداسازی DEMO/REAL وجود دارند.

## 10. دستور اجرای عامل توسعه
1. این سند و docs/SYSTEM_DESIGN.md را با هم مبنای کار قرار بده.
2. ابتدا UI ناوبری و Data Dictionary را طوری طراحی کن که سه طبقه داده از هم جدا باشند.
3. پیش از تولید فرم‌های واقعی، فهرست داده، schema، مالک، ثبت‌کننده، تأییدکننده، فرکانس، موعد و منبع را از تصمیم‌های مصوب دریافت کن.
4. از نام‌ها و مثال‌های این سند برای ساخت داده واقعی، KPI یا نقش قطعی استفاده نکن.
5. هیچ مقدار یا فرمولی برای «تاب‌آوری نقدینگی» اختراع نکن.
6. تا تصویب ماتریس، فقط صفحه مدیریت پیش‌نویس ماتریس و وضعیت «نیازمند تأیید» را فراهم کن؛ وظایف عملیاتی و اعلان‌ها غیرفعال بمانند.
7. قبل از تکمیل UI، قرارداد داده، API، مدل نسخه‌بندی و Audit Trail را طراحی و تست کن.
8. هر تغییر معماری/تصمیم جدید را در docs/DECISIONS.md ثبت کن و معیارهای این سند را به تست‌های قابل اجرا نگاشت بده.
